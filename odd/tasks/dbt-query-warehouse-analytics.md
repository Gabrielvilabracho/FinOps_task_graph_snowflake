# dbt Query and Warehouse Analytics Expansion
Objective: extend the existing native dbt FinOps project with durable query-performance and warehouse-utilization history, then integrate the validated analytics into the operational Task Graph without mixing analytics with warehouse-control actions.
Branch: `feat/dbt-query-warehouse-analytics` from `main` | Delivery: `ask-on-risk`, chain `stacked-to-main` | Runners: repository `unittest`, dbt parse/show/build, and authorized Snowflake validation.

## Specs

- S1 — Start with the dbt project as requested: "entendido. entonces empzamos aplicando priemor los cambio al dbt project apliandolo". Extend the existing `dbt/finops_analytics` project before changing the operational Task Graph.
- S2 — Cover the requested query study: "se puede adicionar el estudio de las queries, que permita entender, las las queries, el timepo de corrido, el tiempoq ue la warehouse no se esta usando pero esta encendida IDLE , P50, P90 , estudio de queries por tiempo asi podemos se entiende cunatas queries se utilizan en x segundos cunatas corren en y segundos diferenciarlas por tiempo". Acceptance: query count, duration buckets, P50, P90 and P99 are available at a documented grain with source-completeness evidence.
- S3 — Build durable history from the oldest Snowflake Account Usage data still available, then capture new data daily. Daily incremental processing must reprocess a bounded recent lookback for late publication; it must not claim to recover data that Snowflake no longer retains.
- S4 — Produce daily, weekly and monthly analytics. Weekly and monthly results must derive from the durable base history, not by averaging weekly percentiles; `P90 monthly != average(P90 weekly)` is an invariant.
- S5 — Extend rather than duplicate the existing dbt foundation. Reuse `stg_account_usage__warehouse_metering_history`, `finops_warehouse_daily`, source-completeness semantics, credential-free profiles, and the dedicated dbt role/warehouse. Add new models only when their grain or materialization has a distinct purpose.
- S6 — Preserve evidence boundaries. `compute_residual_credits` and `estimated_idle_credits` are not exact idle duration, proven waste, or guaranteed savings. Warehouse-on, active, queued and estimated-idle intervals require explicitly documented source evidence and must remain null or incomplete when evidence is insufficient.
- S7 — Keep responsibilities separate: dbt transforms, tests and stores descriptive analytics; native procedures retain approved operational metrics and persisted run state; the Task Graph orchestrates; warehouse suspension remains outside dbt.
- S8 — After dbt models pass local and authorized native validation, integrate the dbt project as one analytical Task Graph node rather than one Snowflake task per dbt model. Preserve the existing nodes and extend the report fan-in only after the dbt execution contract, user-managed warehouse requirement and failure behavior are proven.
- S9 — Generate suspension recommendations only after stable history exists. Any future end-of-day or end-of-week suspension must use a separate control graph with allowlists, active-work checks, `DRY_RUN`, audit records and explicit authorization; no automatic suspension belongs to the first dbt slice.
- S10 — Native Snowflake work is separately authorized. Local implementation does not authorize account access, dbt deployment, task replacement/resume, grants, schedules, warehouse alteration or email delivery. A future native step requires explicit destination, operation and authenticated session authorization.
- S11 — Preserve current production behavior while the expansion is incomplete. Existing Cost/Warehouse marts, procedures, reports and the ten-task operational graph must continue to work; incomplete new analytics must not block the current report until integration is explicitly enabled.
